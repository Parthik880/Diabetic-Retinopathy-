PHASE 1 — EXACT FAILURE AND ROOT CAUSE
The development script launched a RetinaGram process which stayed alive with a
responsive titled Qt window. Returning to the PowerShell prompt did not mean the
development GUI had exited. A controlled earlier dev process closed normally.
The old packaged binary repeatedly exited with -1073741819 / 0xC0000005. Normal
launch and screenshot mode both failed before displaying a window. Stdout and
stderr were empty. Windows Application Error records identified Qt6Core.dll
6.8.3, RVA 0xEAA78. Qt's Windows/image/style plugins were available and loaded.

A temporary native debug-event helper captured the actual exception:
  access violation, read address 0x8, RCX (QObject this) = 0
  Qt6Core+0xEAA78: QObject::doSetProperty+0x28
  caller RetinaGram+0x3311A
Disassembly at that caller showed a loop over seven navigation pointers, loading
a pointer and immediately calling the property setter, with no null-pointer
branch. This corresponds to refreshHeader's active-property loop, called by
buildShell during MainWindow construction. The frontend change had reduced the
center navigation to six buttons and left navButtons_[Cloud] null, while the
old executable still processed all PageCount=7 entries. It dereferenced the
missing Cloud button before MainWindow construction could finish, show() could
run, or QApplication::exec() could start. The navigation loop had the same risk.

The development and packaged executables were different:
  old package SHA256:
  E5B4CA43BB2C3FE18B6BAE8F416FBEBD49BC341CA62D654CF6161EC73FAF7382
  then-current development SHA256:
  1FC2CDB9D87D04FA7298F35BFB2782D814975B3E223E5A099AA5444A37BE9269
Qt6Core.dll was identical between the two environments. The current source
already contained null checks in refreshHeader and navigate when this repair
inspection began. Those checks were preserved, their reason clarified, and the
correct development executable was redeployed. No arbitrary geometry, flags,
hidden startup path, event-loop replacement, or DLL substitution was used.

After that redeployment, before frontend work:
  Release incremental build succeeded (initially no work to do).
  Normal development script/direct launch stayed running and responsive.
  Both development and package windows were visually inspected.
  Normal packaged launch from build/package with Windows-only PATH stayed alive.
  Packaged screenshot mode exited 0 and saved startup-after.png.
The deployment warnings about translations/catalogs.json, dxcompiler/dxil and
OpenSSL remained. Their presence after successful GUI/CUDA runs, and the captured
null QObject stack before repair, establish that they did not cause this startup
regression. A temporary debugger helper and evidence remain under build/validation
and are excluded from the package.
